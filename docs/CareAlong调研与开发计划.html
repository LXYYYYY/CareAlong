消息平台通知、互动消息；互动消息页面为空。尚未验证真实会话、附件、离线通知。我们的 IM 需要单独做跨端验证。
个人中心会员、我的服务、订单、成员、优惠券、就医档案，以及积分、关注、地址、开票、邀请、反馈和客服等入口。第一版保留订单、成员、消息、客服和必要设置；会员营销与扩展档案后续再做。

调研边界：没有提交真实预约、发送消息、上传资料或付款；未进入管理员或服务人员后台；未验证完整订单详情、支付退款、地图实际展示、档案分析及案例详情。因此下文后台和状态规则是本项目的设计建议，并非对参考应用内部实现的描述。

角色第一版页面和能力关键限制

服务人员工作台；资料；可服务院区和时段；待确认预约；接单／拒绝；待服务；开始服务；提交完成；订单沟通。只处理分配给自己的预约；接单前只看判断能否服务所需的最少信息。
管理员网页后台；人员审核；预约审核；服务与价格；医院院区；订单异常；评价与反馈；操作记录。审核、取消、调整必须记录原因和操作者；敏感资料访问需授权并留痕。

同一账号可同时拥有普通用户和已审核服务人员身份，通过工作台切换。管理员权限由后台授予；手机号或前端角色开关都不能自行产生管理员权限。第一版服务人员可由管理员邀请并录入，公开申请入驻可后续开放。

后续阶段：医院代办、跨天照护、优惠券、会员、次数套餐、积分、邀请、礼品卡、复杂开票对接、OCR 挂号资料导入。就医档案中的风险图谱和用药分析是独立产品能力，暂不纳入预约平台的首版工作量。

三 预约与审核规则

已确认：用户先选人员并预约，管理员审核通过后，再由该服务人员确认。建议产品使用“提交预约申请”，避免让用户误以为提交即确定履约。

选择人员与时段→待审核→待人员确认→预约成功→服务中→待用户确认→已完成／待评价
情形建议处理
管理员审核检查资料完整、服务范围、院区、时段与人员匹配；可通过、要求补充或驳回，附原因。业务审核不作医疗诊断。
待审核占用建议先作为申请队列，不承诺锁定资源；提交页明确预约需审核。管理员通过时事务内再次校验并锁定完整服务区间。
人员确认超时为待确认状态设置可配置期限；超时或拒绝后释放占用并通知用户。阈值应按运营时段确定，不能默认全天有人审核。
多人预约同一时段所有状态变化走后端，数据库保证同一人员有效占用区间不重叠。4小时服务需检查整个区间及交通缓冲，不只检查开始小时。
更换服务人员管理员可推荐替代人选，用户确认后重新走必要审核；不得静默替换用户选中的人员。
改期新时段重新校验和确认，原时段在改期成功前保留；事务成功后切换占用，失败仍保留原预约。
取消按当前状态处理，并释放时间占用；涉及已付款订单时退款状态单独跟踪。取消规则在预约前展示。
履约服务人员可在允许的时间窗内开始服务；完成后填写简短服务记录，用户确认。异常由管理员处理并留痕。
评价仅已完成订单可评价，一单一次；投诉和评价分开，避免用评价流程代替异常处理。

支付尚未决定：预约、支付和服务人员结算分别建模。内部试用可用测试支付适配器；生产收费前必须确定收款主体、价格、退款和结算方式。可优先评估“审核及人员确认后，在限定时间内付款”的方案；若选择先付款，则必须完整实现拒绝、超时和取消后的退款。此处不是已确认的商业规则。

需要分别考虑“用户向平台付款”和“平台向服务人员结算”。第一版可支持管理员核对结算台账并人工处理已确认的结算流程；不宜同时引入余额钱包、自动分账和提现系统。

四 单人开发的技术方案

部分建议理由和范围
小程序与 Appuni-app + Vue 3 + TypeScript + Pinia用户与服务人员共用一个工程，复用业务组件；登录、通知、地图和支付集中适配。先使用标准 uni-app，插件验证后锁定版本。
管理后台Vue 3 + Vite + TypeScript + Element Plus桌面表格、筛选和审核操作适合网页后台；与移动端共享接口类型，不强求复用所有界面组件。
后端NestJS 模块化单体 + REST + OpenAPI统一 TypeScript，便于单人维护；账户、人员、预约、履约、消息、支付模块边界清晰。已有熟悉后端技术时可沿用。
数据库PostgreSQL；选择单一 ORM 并锁定版本保存用户、服务、订单和审计；时间区间排斥约束可支持防重复预约。ORM 无法表达的约束通过可审查 SQL 迁移维护。
附件私有对象存储通过业务接口校验访问权限，发短时有效访问地址；开发数据和生产数据隔离。
聊天腾讯云 IM 作为优先验证候选验证文字、图片、历史消息、重连及跨端互通；同一环境三端使用同一 IM 应用，测试与生产分开。
地图uni-app 基础地图能力 + 平台适配第一版医院位置、集合点、打开导航；按供应商配置密钥并核实商用条件。医院坐标统一约定，拒绝定位后可手动选城市。
部署单个后端服务、数据库、对象存储、HTTPS测试与生产隔离，备份、日志和错误告警先到位。任务量增加后再引入专用队列或缓存。

推荐以“一个完整功能”推进：接口、权限、页面和验收一起完成。例如先实现用户预约及管理员审核，再增加人员确认；避免一次生成全部页面后才连接真实数据。

官方能力依据：uni-app TypeScript 支持；IM 小程序与 uni-app 集成；NestJS OpenAPI；PostgreSQL 时间范围与排斥约束。具体依赖组合仍以首阶段实机验证结果为准。

数据组关键对象必须保留的关系
账号与人员users、identities、roles、worker_profiles、worker_reviews业务用户 ID 与微信等登录身份分离；资料审核后才能接单。

服务与排班services、worker_services、availability、schedule_blocks人员可提供的项目、医院和时段相互匹配；有效占用区间不能重叠。
预约与履约orders、order_events、assignments、service_records、reviews每次审核、接单、改期和取消形成记录；订单保留价格和服务描述快照。
沟通与附件conversation_links、attachments、notifications会话关联参与者和业务关系；订单卡片包含订单 ID；附件需校验所属订单权限。
收款与结算payment_attempts、refunds、settlement_records业务订单不等于支付单；同一订单可有多次支付尝试，退款和人员结算单独记录。

接口先围绕真实动作设计：查人员和时段、获取服务报价、提交预约、管理员审核、人员接受／拒绝、取消、改期、开始服务、提交完成、用户确认、评价。每个动作写明允许角色、前置状态、失败原因、幂等规则和审计事件。

金额统一用最小货币单位的整数；预约时间保存完整日期和时区语义；服务时长不能只写在页面标题。服务端生成报价，前端提交报价标识，由后端再次核对，防止价格或时段被篡改。

六 聊天 通知与资料访问

第一版聊天可在服务人员接单后开放，用户与该人员使用一对一会话；同一双方多次预约时通过订单卡片区分业务。若以后需要严格按订单隔离记录，再评估私有会话实现。预约前咨询先由平台客服承接，是否开放直接咨询服务人员仍可调整。

IM 负责消息传输，业务后端决定双方是否允许沟通；密钥和 IM 登录签名在服务端产生。不能只隐藏聊天按钮来限制访问。文字和普通图片作为首版范围；病情附件优先通过有权限控制的订单资料入口查看。

订单状态通知保存在自己的业务数据库，并可重试发送。小程序订阅通知受平台能力及用户授权约束；Android、后续 iOS 需要各自的 App 推送配置。通知失败不能回滚已经成功的订单状态，后台应能看到待处理异常。腾讯云 uni-app 离线推送文档。

资料访问建议：管理员按职责访问；待接单人员仅看服务时间、院区和必要需求；接单后看该订单必要联系方式与资料。公共人员页面不展示服务人员精确实时位置。日志避免记录完整病情、电话或访问令牌。

七 分阶段开发计划

已确认投入：零基础，单人，每周约30小时，使用 AI 辅助。建议以约24至28周、720至840小时作为小范围试运营的初始预算，包含学习、开发、调试与试用缓冲。这是范围估算，不是交付承诺；复杂支付、功能增加或平台材料准备延期需要重新估算，商店审核等待不包含在开发工时内。前3至5周先得到可演示原型和关键技术样例，原型完成不代表生产系统完成。

阶段预计安排交付及完成标准
0 基础与原型第1至3周学习必需的 JavaScript／TypeScript、Vue、Git 和接口概念；冻结首版范围；完成核心原型；能运行、修改并回退一个简单页面。
1 技术验证与工程第4至5周小程序与 Android 实机运行；登录、IM 互发、地图、私有附件验证；检查 iOS 插件并安排构建验证；仓库与测试环境建立。
2 账户与服务目录第6至8周人员审核、院区、服务价格和排班后台；用户可搜索人员、看详情、管理预约成员。
3 预约及审核第9至12周提交预约、管理员审核、人员接受／拒绝；防重复请求和时间冲突；用户可跟踪真实状态。
4 履约及异常第13至15周开始服务、完成确认、评价；取消、改期、超时、重选人员；操作历史可追溯。
5 沟通与通知第16至18周IM、订单卡片、历史消息、断线恢复；通知记录和 App 推送；地图导航与附件权限完成。
6 收费与验收第19至21周若已确定收费形态，接入首个渠道并验证退款、重复回调和对账；否则完成非收费试用版本。完成权限与并发测试、运营手册、备份和发布材料。
7 小范围试用第22至24周用户和少量服务人员试用；修复阻断问题；验证恢复备份与发布回滚；达到验收条件后扩大使用。
8 缓冲第25至28周用于零基础排错、SDK 差异、需求澄清和验收返工；未使用的缓冲不自动替换成新功能。

iOS 从技术验证阶段就检查插件并安排构建验证，业务页面开发时兼顾适配；正式上线可在 Android 流程稳定后独立安排，按当前经验水平另预留约3至6周适配和发布准备缓冲。该区间仍取决于设备、原生插件、登录及支付方案，不包含不确定的商店审核时间。若前期暂缺 iPhone 或构建资源，应记录为未验证项，不能宣称三端验证通过。

按固定工时而非“AI 写代码速度”估算：总时间还包含需求决策、SDK 接入、实机排错、验收与运营准备。每周以能演示的完整流程作为进度依据，不以页面数量或代码行数作为完成标准。

八 必须通过的验收场景

  1. 用户选择人员、院区、时段和就诊人后提交；管理员通过；对应人员接单；三方看到一致状态。
  2. 两笔预约竞争同一人员重叠时段，只能有一个有效占用；服务时长和交通缓冲也计入冲突。
  3. 用户连续点击提交或网络重试，不生成重复订单；重复审核和接单请求不重复产生副作用。
  4. 驳回、人员拒绝及超时有明确提示；时间占用正确释放；更换人员必须得到用户确认。
  5. 改期失败仍保留原预约；改期成功后旧时间释放、新时间占用。
  6. 普通用户、其他服务人员无法读取不属于自己的订单、成员和附件。
  7. IM 断线恢复、历史消息、图片失败重试和多端未读表现可用；通知失败不丢失业务状态。
  8. 定位拒绝、权限取消、无网络和服务器错误均可恢复，用户仍可手动选择院区。
  9. 支付上线时，验证签名、金额、订单身份、重复及乱序回调、退款失败与重试；前端“支付成功”不能直接发放权益。
  10. 数据备份实际恢复成功；关键异常能定位到请求和订单，日志不暴露敏感资料。

九 开发方式与 AI 协作

每周30小时建议分配：8小时学习与理解当前模块，14小时跟随计划实现，6小时实机测试及排错，2小时记录问题与整理版本。随着熟练度提高，将部分学习时间转为开发；保留测试和回顾时间。

学习顺序围绕项目：先掌握变量、对象、数组、函数和异步请求，再理解 Vue 页面与状态、HTTP 接口、数据库和权限。每完成一个模块，应能说清数据来自哪里、谁可以修改、失败怎么恢复，以及如何回退到上一个可运行版本。

每次开发一个可验收的小功能。先写用户故事、允许角色、接口和验收场景，再让 AI 实现，人工检查差异并运行验证，最后提交 Git。每次数据库变更保留迁移脚本，依赖更新单独处理并记录版本。

适合交给 AI 的工作包括页面骨架、接口实现草稿、测试用例、文档和重复结构。订单状态、资源锁定、权限、支付回调和敏感资料访问必须重点审查；这些逻辑应有自动化测试。页面样式和简单可逆调整以人工检查为主。

项目内持续维护四份简短事实来源：需求范围、状态转换表、接口契约、验收清单。每次规则改变先更新约定，再改代码，避免不同页面对同一个订单产生不同解释。

十 近期准备与仍需决定的事项

优先级准备事项完成标志
本周确定首发城市、院区范围、首版服务项目、服务时长和目标人员数量。形成小而明确的服务清单及测试样例。
本周确定审核运营时段、人员确认期限、最短提前预约时间、改期及取消规则。每个异常流程都有明确处理人和状态。
本周准备开发账号、代码仓库、微信测试配置、Android 设备；核实 iOS 构建及真机资源。能够运行最小工程；密钥通过环境配置管理。
第4至5周创建开发专用 IM、对象存储和地图配置，验证三项关键集成。形成可复现的技术样例；测试数据为虚构信息。
收费开发前确定收款主体、付款节点、定价、退款及人员结算；核实发布所需平台材料。形成支付和结算流程，才进入生产收费实现。
扩大试运营前确定谁负责审核、客服和异常处理；建立备份恢复及故障处理流程。有人按时处理预约和异常，系统可恢复。
下一份具体交付应是首版需求规格与原型：人员列表、人员详情、预约表单、用户订单详情、管理员审核、人员接单和履约这七个核心界面，配套订单状态转换表。完成后再开始业务编码。

需要预算的资源类别包括：服务器与数据库、对象存储和流量、IM 套餐、地图商用服务、短信或推送、域名与平台开发者账号、测试设备。先使用开发环境进行小规模验证；正式采购前按实际用量和当时官方价格确认，不将免费额度作为长期成本承诺。

本计划中的技术组合、范围和排期为针对当前需求的建议。已确认的产品约束为：普通用户／管理员／服务人员三类角色，用户选人预约，管理员审核后人员确认，零基础单人借助 AI 开发，每周30小时，首发小程序与 Android，后续兼顾 iOS，暂不开发音视频，支付形态未确定。
